# P1.6 — Parent UPI Payment Integration Release Gate

**Date:** 12 October 2026  
**Branch:** `payment-module-finalization`  
**Scope:** Regression, role/security verification, documentation and release readiness for P1.2–P1.5 UPI payment integration only.

## Scope guard

P1.6 must not add Expenses functionality or any other unrelated feature. Do not delete or rewrite applied migration history. Do not create test payments against real financial records. Use a dedicated test academy, parent, player and due, or obtain an explicitly approved controlled test fixture before executing ledger-mutating scenarios.

## Release checklist

### A. Automated regression

- [x] Latest recorded CI after the rollback passed: 13 Jest suites, 86 tests, production build.
- [ ] Re-run CI after this release-checklist/documentation commit and confirm the run for the resulting head SHA.
- [ ] Review UPI-specific component/service tests and ensure they cover enabled/disabled settings, QR-only configuration, WhatsApp share content, invalid claim fields, duplicate UTR, over-balance claims, and recorded-vs-accepted status.
- [ ] Confirm no unrelated Expenses UI/service behavior or test files were reintroduced by P1.6.

### B. Academy UPI settings (P1.2)

- [ ] Academy Owner can save and edit UPI ID/payee/QR details for their own academy.
- [ ] Academy Owner cannot read or mutate another academy's settings or QR objects, including direct ID/path tampering.
- [ ] Super Admin can inspect settings but cannot mutate them.
- [ ] Disabled settings are not presented to parents as active payment instructions.
- [ ] QR-only configuration renders correctly when no UPI ID is configured; malformed values are rejected.
- [ ] QR object permissions match the intended public-read and owner-only academy-path mutation model.

### C. Parent display and sharing (P1.3)

- [ ] Parent sees only UPI instructions belonging to the selected linked child's academy.
- [ ] Switching linked children refreshes the academy-specific details correctly.
- [ ] QR image and UPI details render correctly for enabled settings; disabled settings do not expose stale instructions.
- [ ] WhatsApp share action is user initiated and contains the correct academy/payee/UPI ID/QR URL.
- [ ] Existing dues, payment history and receipt display remain unchanged.

### D. Submission and review security (P1.4)

- [ ] Parent can submit a valid claim only for a linked child's outstanding due.
- [ ] Reject missing due, non-positive amount, amount greater than current remaining balance, short/duplicate UTR, missing date, future date and overlong note.
- [ ] Parent can read only their own claims; another parent cannot read the claim or submit against the first parent's child/due.
- [ ] Academy Owner can read/review only claims for their academy.
- [ ] Super Admin is read-only in the review UI and the RPC rejects their review attempt.
- [ ] Coach and anonymous access to claim data and submission/review RPCs is denied.
- [ ] Rejection requires a reason of at least three characters; a reviewed claim cannot be reviewed twice.
- [ ] A second pending/accepted claim for the same due and duplicate academy UTR are blocked.
- [ ] Accepting/rejecting a claim alone does not create a payment, change due balances/status or issue a receipt.

### E. Accepted-claim ledger recording (P1.5)

Use a dedicated test due and capture its starting state before testing.

- [ ] Only an Academy Owner scoped to the claim's academy can record it.
- [ ] Pending, rejected, missing and cross-academy claims are rejected by the recording RPC.
- [ ] An accepted claim that is now stale or exceeds the current remaining balance is rejected with no partial writes.
- [ ] Successful recording creates exactly one payment through `collect_payment`, with payment mode `upi`.
- [ ] The parent-submitted UTR is stored as `payments.external_transaction_reference`.
- [ ] The existing receipt-number workflow returns a receipt; the claim stores the corresponding `payment_id`, `recorded_by_user_id`, `recorded_at`, and `recorded` status.
- [ ] The due's paid amount, remaining amount and status match the newly recorded collection.
- [ ] Repeating the record action or invoking the RPC again does not create another payment or receipt.
- [ ] Force/observe a rollback-safe failure on a dedicated test fixture and confirm payment, due, claim and receipt state are not partially committed.
- [ ] Confirm Parent Portal payment history and receipt display show the recorded collection correctly.
- [ ] Coach, Parent, Super Admin and anonymous callers cannot record a claim; a different Academy Owner cannot record it across academy boundaries.

### F. Data integrity and regression

- [ ] Before/after snapshots for test fixtures reconcile claim status, payment count, payment amount/reference/receipt, and due paid/remaining/status.
- [ ] No production customer payment or due was used as a mutation test fixture.
- [ ] Existing manual payment collection, receipts, payment correction workflow and parent payment history still work.
- [ ] No historical migration file or migration-ledger row was deleted, renamed or rewritten.
- [ ] Re-run the Supabase Security Advisor; record deltas against the documented baseline rather than blindly revoking intentional RPC execution.
- [ ] Review the final Git diff/status and confirm the changes are limited to UPI regression/release documentation.

### G. Release decision

Release is **blocked** until all required browser/security scenarios above are passed on an accessible preview and CI is green for the final head. Record the tester, test fixture IDs (non-sensitive), date, pass/fail result and evidence for each scenario. If Vercel preview remains unavailable, leave browser acceptance pending and do not infer a pass from automated tests or database introspection.
