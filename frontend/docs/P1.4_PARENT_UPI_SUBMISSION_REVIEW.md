# P1.4 — Parent UPI Payment Submission and Verification

**Branch:** `payment-module-finalization`  
**Implementation date:** 12 October 2026  
**Status:** P1.4/P1.5 implemented; automated validation and live schema/grant checks passed; browser acceptance pending

## Scope

P1.4 lets a parent submit a UPI payment claim against a linked child's outstanding fee due. An Academy Owner reviews the claim in a dedicated queue. Super Admin can inspect claims read-only. Coach and anonymous access are denied.

Submission and review are separate from ledger posting: **submitting or accepting/rejecting a claim does not create a row in `public.payments`, update `public.payment_dues`, change balances, or issue a receipt.** P1.5 adds an explicit Academy Owner action to record an accepted claim through the existing secured `collect_payment` workflow.

## Parent submission

The Parent Financial Overview displays the form only when UPI payment details are enabled for the selected child's academy. The parent selects an outstanding due and enters:
- Amount paid (positive, at most the current remaining due)
- UPI transaction reference / UTR (3–120 characters)
- Payment date (cannot be in the future)
- Optional note (maximum 500 characters)

The `submit_parent_upi_payment` RPC verifies the authenticated parent role, parent profile, child-to-parent link, due-to-player link, current due balance and academy scope. A unique academy/reference index prevents reusing a UTR. A unique partial index allows only one pending or accepted claim per due.

## Review queue

Route: `/parent-upi-submissions`

- Academy Owner sees and reviews claims scoped to the current academy.
- Super Admin can inspect all claims but has no review actions.
- Accepting or rejecting a claim is performed by `review_parent_upi_payment`.
- Rejection requires a reason of at least three characters.
- Review RPC rechecks the due balance before accepting and rejects stale or over-balance claims.
- A claim can be reviewed only while pending; repeated review attempts are rejected.

## Database and security

Migrations:
- `20261012023354_parent_upi_payment_submissions.sql`
- `20261012023526_parent_upi_submission_invariants.sql`

Table: `public.parent_payment_submissions`

RLS is enabled. Authenticated clients have SELECT only; INSERT/UPDATE/DELETE are not granted. Mutations are limited to two authenticated SECURITY DEFINER RPCs with empty search paths and explicit role, identity, relationship, academy-scope and business-rule checks. Anonymous and PUBLIC EXECUTE are revoked.

The review queue does not use frontend filtering as the security boundary. RLS and RPC authorization enforce scope at the database layer.

## P1.5 — Record accepted claim to ledger

Migration: `supabase/migrations/20261012025707_parent_upi_claim_ledger_recording.sql` (live ledger version `20261012025707`). The Academy Owner can explicitly record an accepted claim. The SECURITY DEFINER wrapper has an empty search path, checks owner role and academy scope, locks and revalidates the due, calls the existing secured `collect_payment` RPC, stores the parent-reported UTR on the created payment, and marks the claim `recorded` with its payment ID and recording metadata. The wrapper is transactional, so a failure rolls back the payment, due update, receipt creation and claim update together. A unique payment-link index and claim status guard prevent duplicate recording.

Live schema/grant inspection on 12 October 2026 confirmed the P1.4/P1.5 migrations are recorded, RLS is enabled, authenticated table access is SELECT-only, the required indexes and policies exist, and `submit_parent_upi_payment`, `review_parent_upi_payment`, `record_accepted_parent_upi_submission`, and `collect_payment` use empty search paths with anon EXECUTE denied. This is database inspection, not browser acceptance.

## Browser acceptance checklist

1. Parent can submit a valid claim for a linked child and outstanding due.
2. Parent cannot submit for an unlinked child or another academy's due (negative test).
3. Missing/invalid amount, future date, short/duplicate UTR and over-balance amount are rejected.
4. Parent sees only their own claim history.
5. Academy Owner sees only claims for their academy.
6. Super Admin can view claims but cannot accept/reject them.
7. Accept requires the claim still fit within the current remaining due.
8. Reject requires a reason; a reviewed claim cannot be reviewed again.
9. A second pending/accepted claim for the same due is blocked.
10. After submission and after accept/reject, compare `payments`, `payment_dues.paid_amount`, `remaining_amount`, `due_status` and receipts: all financial ledger values must remain unchanged.
11. Coach and anonymous users cannot read or mutate claims or invoke the submission/review RPCs.

## Known boundary

An accepted claim means the Academy Owner has verified the submitted details; it is not yet a ledger payment or receipt. The Owner must use the explicit **Record payment & issue receipt** action to invoke P1.5. Browser acceptance for P1.2–P1.5 remains pending; use the full test matrix in `docs/P1.6_UPI_RELEASE_CHECKLIST.md` before release.
